# Deliverables Memory Management Architecture

Memory state management and context flow in the PPTX/DOCX/XLSX rendering pipeline.

## 1. Overview: Three-Layer Memory Model

The deliverables section manages memory across three distinct layers:

### Layer 1: Transient State
In-memory payload dictionaries during render phase. Thread-safe with RLock synchronization.

### Layer 2: Persistent Context
Branding context (ColorPalette, BrandingContext) loaded from ProjectBrand table or defaults.

### Layer 3: File Storage
Final artifacts (.pptx, .docx, .xlsx) written to `workspace/{project_id}/runs/{run_id}/artifacts/`

**Key Design:** Deliverables are stateless renderers—no internal caching. All context passed as arguments from orchestrator.

---

## 2. DeliverableRegistry: Thread-Safe Singleton

**Location:** `src/deliverables/deliverable.py`

```python
class DeliverableRegistry:
    _lock = RLock()
    _deliverables: dict[str, IDeliverable] = {}

    @classmethod
    def register(cls, output_type: str, deliverable: IDeliverable):
        with cls._lock:
            cls._deliverables[key] = deliverable

    @classmethod
    def get(cls, output_type: str) -> IDeliverable:
        with cls._lock:
            return cls._deliverables.get(key)
```

### Lazy Initialization:
- Implementations registered on module load via `_init_default_deliverables()`
- Guard: `if DeliverableRegistry._deliverables: return` prevents re-registration
- Factory pattern: Each output type (pptx, docx, xlsx, pdf) is a stateless renderer instance

## 3. BrandingService: Context Assembly

**Location:** `src/deliverables/branding_service.py`

### Branding Hierarchy (Priority Order):

| Level | Source | Memory Location | TTL |
|-------|--------|-----------------|-----|
| `RUNTIME_OVERRIDE` | Runtime flags / API params | Ephemeral (request scope) | Single request |
| `SKILL_OVERRIDE` | Skill output payload | In-memory during render | Render lifetime |
| `INGESTED_DESIGN_SYSTEM` | Wiki/OneDrive design tokens | ProjectBrand.design_system_json | Project lifecycle |
| `PROJECT_CUSTOM` | ProjectBrand row (custom colors/logo) | Database (ProjectBrand FK) | Indefinite |
| `DELOITTE_DEFAULT` | Hardcoded defaults | Code constant | N/A |

```python
@dataclass
class BrandingContext:
    level: BrandingLevel
    primary_color: str
    palette: ColorPalette
    font_family: str
    logo_url: str | None
    deck_theme: str  # "" = unset, "classic" or "editorial"
```

## 4. Render Pipeline: Memory Flow

```
orchestrator.py (run execution)
         │
         ▼
assemble_context()
    ├─→ Tier 0: CONTEXT.md (2,000 chars)
    ├─→ Tier 1: LP snippets (12,000 chars)
    ├─→ Tier 2: BM25-ranked docs (10,000 chars)
    └─→ Tier 3: Conversation digest (variable)
    
         ▼ [ContextBundle: 32,000 chars max]
         
LLM API call
    └─→ Generate skill payloads (pptx_data, docx_data, xlsx_data)
    
         ▼ [Response in memory]
         
charge_llm_usage()
    ├─→ _RunTokenUsage.charge(input, output, cache_read, cache_create)
    └─→ Metrics: prompt_compression_applied_total
    
         ▼ [Token budget tracked]
         
DeliverableRegistry.get(output_type)
    └─→ PayloadHandler.render(payload, run_dir, branding)
    
         ▼ [Render phase: in-memory transformation]
         
PPTX/DOCX/XLSX Renderer
    ├─→ _merge_branding_dict(branding) → flat dict
    ├─→ Compose slides/paragraphs with colors/fonts
    ├─→ Apply core properties (title, author, keywords)
    └─→ Write to disk: workspace/.../artifacts/
    
         ▼ [Final file: .pptx, .docx, .xlsx]
         
extract_quality_signals(artifact_path)
    └─→ PPTX QA: slide count, completeness checks
         XLSX QA: cell count, formula validation
```

## 5. Payload State: Ephemeral In-Memory Dicts

### Payload Structure (Generated by LLM):

#### For PPTX
```json
{
    "slides": [
        {
            "title": "Opening",
            "body": "Content",
            "speaker_notes": "Notes...",
            "layout_type": "title_only"
        }
    ],
    "metadata": {
        "deck_title": "Sales Deck Q4",
        "audience": "finance_team"
    }
}
```

#### For DOCX
```json
{
    "sections": [
        {"heading": "Executive Summary", "paragraphs": [...]}
    ],
    "front_matter": {"title": "...", "date": "..."}
}
```

#### For XLSX
```json
{
    "sheets": [
        {
            "name": "Dashboard",
            "rows": [[col1, col2, ...], ...]
        }
    ]
}
```

### Memory Characteristics:
- **Lifetime:** Created by LLM response, consumed by render(), then GC'd
- **Size:** Typically 50KB–500KB (text-based, no images)
- **Thread Safety:** Single-threaded per render call (no concurrent access)
- **Mutation:** Applied in-place by `apply_branding()` and `humanize_deep()`
- **Validation:** JSON schema checked before render

## 6. Branding Application: Deep Merge Strategy

### Flow:

1. `BrandingService.get_for_project(project_id, level)` loads from DB/defaults
2. `_merge_branding_dict(branding)` flattens dataclass to dict:
   - Primary color → RGB hex
   - Palette → accent colors
   - Font → resolved to system fonts
   - Logo URL → validated + fetched via SSRF-safe `safe_get()`

3. `apply_branding(payload, branding)` injects colors into payload:
   - PPTX: Color → RGBColor in shapes/text
   - DOCX: Color → Heading styles, footer
   - XLSX: Color → cell fills, borders

4. Render writes final file with applied branding

```python
def apply_pptx_core_properties(prs, title, subject, author, ...):
    cp = prs.core_properties
    cp.title = title[:255]          # Truncated
    cp.subject = subject[:255]
    cp.author = author[:255]
    cp.keywords = "advise_workbench,pptx"
    cp.created = datetime.now(IST)
    cp.modified = datetime.now(IST)
```

## 7. Cache Strategy: No Artifact Caching

**Principle:** Deliverables are stateless. Each render is independent.

| Layer | What's Cached | Where | Invalidation |
|-------|---------------|-------|--------------|
| Branding | ProjectBrand row | Database (ORM) | Manual update to ProjectBrand |
| Registry | Deliverable implementations | Module dict (singleton) | Never (app lifetime) |
| Logo | Downloaded image binary | Temp file (auto-GC'd) | End of render |
| Artifacts | PPTX/DOCX/XLSX files | Filesystem | Manual deletion (workspace cleanup) |

**Why No Artifact Cache?** Payloads are LLM-generated and unique per run. Re-rendering identical skill output is negligible compared to LLM cost.

## 8. Quality Signals: Post-Render Extraction

**Location:** `src/evaluation/pptx_qa.py`, `deliverable_quality.py`

### PPTX Metrics (In-Memory):
- **Slide count:** `len(prs.slides)` vs `MAX_RENDERED_SLIDES`
- **Completeness:** Title/body text per slide
- **Layout consistency:** Detected layout types (title_only, content, 2-column)
- **Media:** Embedded charts/images (memory-heavy; streamed via chunks)

### XLSX Metrics:
- **Cell count:** Rows × columns (memory footprint)
- **Formulas:** Validation engine (Openpyxl in-memory)
- **Formats:** Applied styles count

### Metrics Returned:
```json
{
    "artifact_path": "/workspace/run_id/artifacts/deck.pptx",
    "slide_count": 12,
    "completeness_score": 0.92,
    "quality_flags": ["missing_speaker_notes_slide_5"]
}
```

## 9. Memory Cleanup & Lifecycle

### Cleanup Phases:

| Object | Scope | Cleanup Trigger | Manual Cleanup Needed? |
|--------|-------|-----------------|----------------------|
| Payload dict | Request scope | After render() completes | No (automatic GC) |
| Branding dict | Request scope | After apply_branding() | No (automatic GC) |
| Logo image temp file | Render lifetime | End of render; tempfile auto-deleted | No (tempfile module) |
| PPTX/DOCX in-memory | Render lifetime | After .save() to disk | No (auto-GC when closed) |
| Artifact files | Run lifetime | Manual: `rm workspace/.../artifacts/*` | Yes (per retention policy) |

**Note:** No memory leaks in deliverables. Context managers and Python's GC handle object lifecycle automatically. Artifact retention is a policy decision (how long to keep .pptx/.docx files).

## 11. Integration with Broader Memory System

### Where Deliverables Sit in the Stack:

```
Tier 3: Conversation Digest (CompactionTrace)
    │ [32,000 char context budget]
    ▼
Tier 3.5: LLM Call
    │ [Claude API with prompt caching]
    ▼
Skill Output (Payload Dicts)
    │ [Generated by LLM; ephemeral]
    ▼
← DELIVERABLES LAYER →
│
├─ BrandingService (ProjectBrand FK)
├─ DeliverableRegistry (singleton)
├─ Render Pipeline (stateless)
├─ Quality Extraction (post-render)
└─ File Storage (workspace/artifacts/)
```

### Key Interactions:
- **Context Assembly:** Deliverables receive full context as input (no separate retrieval)
- **Memory Events:** No direct memory writes. Skill outputs may be logged to MemoryEvent for audit.
- **Consent:** Branding is project-scoped; no PII in payloads (enforced upstream)
- **Token Budgets:** Deliverables don't consume LLM tokens (rendering is deterministic)
- **Cache TTL:** Artifacts not cached; branding cache is DB-managed

## 12. Quick Reference: Memory Management Summary

| Concern | Pattern | Scope | Location |
|---------|---------|-------|----------|
| Payload State | Ephemeral dict; single-threaded | Request lifetime | In-memory; LLM → render → GC |
| Branding Context | DB-backed; deep-merged into payload | Project lifetime | ProjectBrand table; applied at render |
| Renderer Instances | Singleton factories (thread-safe RLock) | App lifetime | DeliverableRegistry; lazy-loaded |
| Artifacts | File storage; no in-memory cache | Run lifetime | workspace/{project_id}/runs/{run_id}/artifacts/ |
| Quality Signals | Post-render extraction (in-memory QA) | Render lifetime | extract_quality_signals() result |
| Logo Images | Temp file; auto-GC via tempfile module | Render lifetime | System temp; fetched via SSRF-safe handler |
