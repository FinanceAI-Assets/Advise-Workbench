# Monitoring with OpenObserve

The backend sends traces, metrics and logs to [OpenObserve](https://openobserve.ai) over OpenTelemetry (OTLP/HTTP). OpenObserve is one binary with a web interface; no Docker is needed.

## Set-up on one machine

```bash
./scripts/openobserve.sh setup   # downloads the binary (about 120 MB) and writes OPENOBSERVE_* into .env
./scripts/run_agent.sh           # starts OpenObserve with the bridge, backend and frontend
```

Open http://localhost:5080 and sign in with `OPENOBSERVE_USER` and `OPENOBSERVE_PASSWORD` from `.env`. The password is generated by `setup`.

| File | Purpose |
|---|---|
| `scripts/openobserve.sh` | `install`, `setup`, `start`, `status` |
| `scripts/openobserve_query.py` | Query OpenObserve from the command line with the `.env` settings |
| `.tools/openobserve/` | The binary (not in git) |
| `workspace/.openobserve/` | OpenObserve's data (not in git) |

## Settings

| Setting | Default | Meaning |
|---|---|---|
| `OPENOBSERVE_ENABLED` | `false` | Switch telemetry on |
| `OPENOBSERVE_URL` | `http://localhost:5080` | Where OpenObserve listens |
| `OPENOBSERVE_ORG` | `default` | OpenObserve organisation |
| `OPENOBSERVE_USER`, `OPENOBSERVE_PASSWORD` | empty | Sign-in used to send and to query |
| `OPENOBSERVE_STREAM` | `advise_workbench` | Stream name for traces and logs |

To use a hosted OpenObserve, set the URL, organisation and sign-in; do not run `openobserve.sh start`.

With `OPENOBSERVE_ENABLED=false` nothing is sent and the tracing calls in the code do nothing.

## What is sent

### Traces (stream `advise_workbench`, type traces)

| Span | Opened in | Attributes |
|---|---|---|
| `http.request` | `src/core/middleware.py` | `http.method`, `http.route`, `correlation_id` |
| `conversation.turn` | `src/workflows/conversation_graph.py` | `project_id` |
| `conversation.phase.receive` / `understand` / `route` / `respond` | same | |
| `run.execute` | `src/workflows/orchestrator.py` | `project_id`, `run_id` |
| `run.phase.prepare` / `context` / `generate` / `evaluate` / `remember` / `finalize` | `src/workflows/agent_graph.py` | `run_id`, `project_id`, `graph.thread_id`, and `run.outcome_ok`, `run.outcome_error` when the phase ends the attempt |
| `run.coordinator` and the document agent spans | `src/agents/` | |
| `llm.call` | `src/llm/gateway.py` (every model call) | `gen_ai.system` (provider), `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reason`, `llm.tools` |
| `rag.lp` and `rag.lp.load_index` / `prepare_query` / `keyword` / `semantic` / `fuse` / `select` / `generate` | `src/memory/knowledge/lp_rag.py` | `rag.query_chars`, `rag.results`, and the size of each step's output |

A span that renders a registry prompt also carries `prompt.name` and `prompt.version`.

One conversation turn is one trace: the turn, its four phases, and the model calls inside each phase. One run attempt is one trace: `run.execute`, its six phases, the coordinator, and every model call. Document agents run in worker threads; `with_trace_context` keeps their spans in the run's trace.

### Metrics

Every counter, gauge and latency recorded through `src/core/observability/metrics.py` is also sent as an OpenTelemetry metric with the same name (latencies as `<name>_ms` histograms). New with this change:

| Metric | Meaning |
|---|---|
| `llm_calls_total`, `llm_input_tokens_total`, `llm_output_tokens_total` | Model calls and tokens |
| `llm_call_ms` | Model call duration |
| `lp_rag_searches_total`, `lp_rag_answers_total` | Leading Practice library searches and answers |

Existing ones include `run_done_total`, `run_failed_total`, `run_execution_ms`, `conversation_digest_built_total` and the `memory_*` counters. `GET /metrics/prometheus` still works.

### Logs (stream `advise_workbench`, type logs)

Every Python log record at INFO or above, with the trace id when it was written inside a span, so a log line links to its trace.

## Looking at the data

In the OpenObserve web interface: **Traces** (pick stream `advise_workbench`) shows each turn and run as a timeline; **Logs** searches log lines; **Metrics** charts the counters.

From the command line:

```bash
# What has arrived
python scripts/openobserve_query.py streams

# Slowest model calls in the last hour
python scripts/openobserve_query.py sql "SELECT operation_name, duration, gen_ai_request_model, gen_ai_usage_output_tokens FROM advise_workbench WHERE operation_name = 'llm.call' ORDER BY duration DESC LIMIT 20" --type traces

# The phases of one run
python scripts/openobserve_query.py sql "SELECT operation_name, duration, run_outcome_ok, run_outcome_error FROM advise_workbench WHERE run_id = '<run id>' ORDER BY _timestamp" --type traces --minutes 180

# Warnings and errors
python scripts/openobserve_query.py sql "SELECT severity, body FROM advise_workbench WHERE severity IN ('WARNING', 'ERROR') ORDER BY _timestamp DESC LIMIT 50"
```

OpenObserve replaces dots in attribute names with underscores (`run.outcome_ok` is the column `run_outcome_ok`). Span durations are in microseconds.

## Limits

- No dashboards or alerts are shipped; build them in the OpenObserve interface from the streams above.
- With the Claude CLI bridge, input token counts are reported as 0 by the bridge, so `gen_ai.usage.input_tokens` is 0.
- Langfuse tracing (`LANGFUSE_ENABLED`) and `OTEL_SDK_ENABLED` (traces only, to any OpenTelemetry collector) still exist and are independent of OpenObserve.
